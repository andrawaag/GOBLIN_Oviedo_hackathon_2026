# Approach — rendering SSSOM mappings as RDF 1.2 triple terms

> **Status: first draft / proposal.** This document and the accompanying serializer are an
> early proposal meant to *initiate a conversation*, not a finished specification. The reference
> script was **generated by prompting a large language model (Claude)** and has **not** been
> hand-audited or validated against the SSSOM community model. Several IRIs still need to be
> **properly minted** (see [Caveats](#caveats--what-still-needs-doing)).

## What SSSOM is

SSSOM (Simple Standard for Sharing Ontological Mappings) is widely used in bioinformatics to
share mapping files between datasets and ontologies. Although the files carry some ontological
commitments, they are most often consumed as plain dataframes. A SSSOM file is two parts in one:
a **YAML metadata header** carried in `#`-prefixed comment lines, followed by a
**tab-separated (TSV)** table of mappings.

```
#curie_map:
#  EXT: https://example.org/properties/
#  FOODON: http://purl.obolibrary.org/obo/FOODON_
#  KF_FOOD: https://kewl-foodie.inc/food/
#  ORCID: https://orcid.org/
#mapping_set_id: https://example.org/sample-set
#mapping_set_description: Manually curated alignment of KEWL FOODIE INC internal food and
#  nutrition database with Food Ontology (FOODON).
#license: https://creativecommons.org/licenses/by/4.0/
#mapping_date: 2025-07-14
#extension_definitions:
#  - slot_name: ext_fooable
#    property: EXT:isFooable
#    type_hint: xsd:boolean

subject_id      predicate_id     object_id        mapping_justification
KF_FOOD:F001    skos:exactMatch  FOODON:00002473  semapv:ManualMappingCuration
```

## Each mapping is a triple, annotated as an RDF 1.2 triple term

SSSOM is clearly RDF-inspired: the core of each row — `subject_id`, `predicate_id`, `object_id` —
*is* a triple. We therefore translate each row into a single **asserted triple**, then attach all
remaining SSSOM data to that triple via an RDF 1.2 **triple term** (reification).

Using the Turtle 1.2 annotation syntax:

```turtle
PREFIX sssom:   <https://w3id.org/sssom/>
PREFIX semapv:  <https://w3id.org/semapv/vocab/>
PREFIX dcterms: <http://purl.org/dc/terms/>
PREFIX skos:    <http://www.w3.org/2004/02/skos/core#>

KF_FOOD:F001 skos:exactMatch FOODON:00002473 {|
    sssom:mapping_justification semapv:ManualMappingCuration ;
    dcterms:license <https://creativecommons.org/licenses/by/4.0/> ;
    sssom:mapping_date "2025-07-14"^^xsd:date
|} .
```

which desugars to an asserted triple **plus** a reifier over the triple term:

```turtle
KF_FOOD:F001 skos:exactMatch FOODON:00002473 .

_:m rdf:reifies <<( KF_FOOD:F001 skos:exactMatch FOODON:00002473 )>> ;
    sssom:mapping_justification semapv:ManualMappingCuration ;
    dcterms:license <https://creativecommons.org/licenses/by/4.0/> ;
    sssom:mapping_date "2025-07-14"^^xsd:date .
```

Syntax notes (these correct common slips):

- The RDF 1.2 triple term is written **`<<( s p o )>>`** — parentheses, **object position only**,
  and **no trailing `.`** inside it. (`<< s p o >>` without parentheses is the older RDF-star
  quoted-triple form.)
- The triple term is **opaque and non-asserting**; the base triple is asserted separately.
- Propagatable header slots (here `license` and `mapping_date`) are carried down onto each mapping.
- We use `sssom:mapping_justification semapv:ManualMappingCuration` (a property), consistent with
  the SSSOM model and the serializer. (An alternative some drafts use is `a
  semapv:ManualMappingCuration`, i.e. *typing* the mapping; we did not take that route.)

## CURIE expansion and IRI-unsafe local names

SSSOM's header CURIE map is treated as **authoritative** for expanding prefixes to IRIs. However,
some local-name parts are not valid for direct use inside an IRI. The canonical case is the
`SMILES:` "prefix", which is not really an identifier namespace but a chemical-structure notation
pressed into service as an identifier. SMILES (and InChI) strings contain `/`, `#`, `[`, `]`, `=`,
… which IRI syntax forbids. We **percent-encode the local part** (per RFC 3987), leaving the
namespace literal, so the result is a syntactically valid IRI.

## Scope decisions / deviations from existing SSSOM-RDF

- **No literal-subject mappings.** SSSOM/TSV permits mappings between literals, e.g.
  `"hello"@en skos:closeMatch "hallo"@nl`. That is *generalized* RDF (a literal in subject
  position), which RDF 1.2 triple terms do not support. As most datasets and tooling do not use
  generalized RDF, we accept that this excludes a small number of SSSOM files.
- **Per-mapping, not per-file.** Existing SSSOM/RDF describes the mapping *set as a whole*. This
  RDF 1.2 approach instead describes **each mapping independently**, as a self-contained annotated
  triple (with at most a lightweight back-link to its set). This is also why the repository ships a
  *complementary* **named-graph (TriG)** rendering, which keeps the set-as-a-whole view — one graph
  per mapping set. See [schema-named-graphs.md](schema-named-graphs.md) and
  [schema-rdf12.md](schema-rdf12.md).

## Caveats — what still needs doing

This is a **proposal**, and the rendered files need proper validation before any reuse:

1. **IRIs must be minted.** Two IRIs the serializer emits under `w3id.org` are placeholders we do
   **not** own and have **not** registered:
   - `https://w3id.org/sssom/mapping_set` — a convenience predicate linking a mapping back to its
     set. It is **not** a standard SSSOM slot and needs to be minted or replaced with an agreed term.
   - `https://w3id.org/sssom/.well-known/curie/{prefix}/{local}` — the fallback IRI used when a
     CURIE prefix is missing from the `curie_map`. It needs a real resolution policy. (In the OLS
     run no fallback was triggered, but the mechanism exists.)
   - The reused `sssom:` slot IRIs (`mapping_justification`, `subject_label`, `object_label`,
     `MappingSet`, `mapping_set_confidence`, `mapping_set_source`, `mapping_set_group`) are
     **assumed** to match the official SSSOM model and must be **verified** against it.
2. **Modelling not yet validated.** The outputs parse with a strict RDF 1.2 parser (pyoxigraph),
   but parsing ≠ correct modelling. The shapes need review against the SSSOM community.
3. **LLM-generated code.** The serializer ([../scripts/sssom_serialize.py](../scripts/sssom_serialize.py))
   was produced by prompting Claude. Treat it as a starting point to be audited, not a reference
   implementation.

## Implementation status

The current reference script emits the **EBI OLS column set** — `mapping_justification`,
`subject_label`, `object_label` — plus the `sssom:mapping_set` back-link. The propagatable header
slots shown in the example above (`license`, `mapping_date`) and `extension_definitions` are part of
the *proposed* approach but are **not yet implemented** in the script.
